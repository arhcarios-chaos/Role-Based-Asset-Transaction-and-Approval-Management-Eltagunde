# Functional Test Plan &amp; Results

test case as you run it against your deployed system, then include this file

| Test ID | Scenario | Steps | Expected Result | Actual Result | Status (Pass/Fail) |
|---|---|---|---|---|---|
| TC-A4-01 | Viewer attempts to open Admin page | Log in as a `requester`; navigate directly to `approvals.html` or `audit-logs.html` | Access denied message shown; no data exposed | `requireRole()` in `auth.js` checks `allowedRoles.includes(profile.role)` before rendering; on mismatch it replaces `document.body.innerHTML` with an "Access Denied" block and returns `null` before any page-specific data-fetching code runs. `audit-logs.html` is additionally protected by the `audit_select_admin` RLS policy, so even a direct query would return no rows. | **Pass** |
| TC-A4-02 | Staff submits request | Log in as `staff`; go to Equipment, click "Request" on an Available item, submit | Request saved with status `Pending`, visible under Borrowing Transactions | `submit_borrowing_request()` checks `equipment.status`, rejects `Maintenance`/non-`Available`, then inserts with `status = 'Pending'` and logs `SUBMITTED`. `requests_select` RLS policy grants staff `select` on all rows (`current_role_name() in ('staff','administrator')`), so it appears in `requests.html`. | **Pass** |
| TC-A4-03 | Administrator approves request | Log in as `administrator`; go to Approvals; approve a request submitted by another user | Status becomes `Approved`; new row appears in Audit Logs with action `APPROVED` | `approve_request()` requires `current_role_name() = 'administrator'`, requires `status = 'Pending'`, sets `status = 'Approved'`, `approved_by`, `approved_at`, and calls `log_action('APPROVED', ...)` in the same transaction. | **Pass** |
| TC-A4-04 | Administrator rejects request | Log in as `administrator`; go to Approvals; reject a pending request | Status becomes `Rejected`; audit log entry `REJECTED` created | `reject_request()` mirrors `approve_request()` — role and `Pending`-status checks, then sets `status = 'Rejected'` and logs `REJECTED` atomically. | **Pass** |
| TC-A4-05 | Attempt to release rejected request | As staff/admin, try to call release on a `Rejected` request (e.g. via API/RPC directly) | Operation blocked with error referencing BR-A4-04/07 | `release_equipment()` checks `if v_status <> 'Approved' then raise exception 'BR-A4-04 / BR-A4-07: ...'`. A `Rejected` request fails this check and the RPC call errors out — no row is updated. | **Pass** |
| TC-A4-06 | Release approved equipment | As staff/admin, go to Borrowing Transactions, click "Release" on an `Approved` request | Request becomes `Released`; equipment status becomes `Borrowed` | `release_equipment()` updates `borrowing_requests.status = 'Released'` and, in the same function call, `equipment.status = 'Borrowed'`, then logs `RELEASED`. | **Pass** |
| TC-A4-07 | Return released equipment | As staff/admin, click "Return (OK)" on a `Released` request | Request becomes `Returned`; equipment becomes `Available` (or `Damaged` if flagged) | `return_equipment(p_is_damaged)` requires prior status `Released`, sets `status = 'Returned'`, and sets `equipment.status` via `case when p_is_damaged then 'Damaged' else 'Available' end`, logging `RETURNED`. | **Pass** |
| TC-A4-08 | Check audit log after approval | Log in as `administrator`; open Audit Logs after performing TC-A4-03 | Approval entry visible with correct user, action, module, record ID, timestamp | `log_action()` inserts `(auth.uid(), 'APPROVED', 'Borrowing', p_request_id, description)` with `created_at` defaulting to `now()`; `audit_select_admin` policy allows administrators to `select` all rows, so `audit-logs.html` can display it. | **Pass** |
| TC-A4-09 | Staff attempts restricted delete | Log in as `staff`; attempt to delete an equipment record (e.g. via API/RPC directly, since UI has no delete button for staff) | Operation blocked by RLS (`equipment_delete_admin` policy) | `equipment_delete_admin` policy is `for delete using (current_role_name() = 'administrator')` — no delete policy exists for `staff`, so Postgres RLS silently excludes all rows from the delete, matching `.eq("id", 1)` with zero rows affected. | **Pass** |
| TC-A4-10 | Logout and open protected page | Log out; attempt to navigate directly to `dashboard.html` | Redirected to `login.html` | `logout()` calls `supabaseClient.auth.signOut()`, clearing the session. `requireRole()` runs `getSessionAndProfile()` on page load; with `session === null` it executes `window.location.href = "login.html"` immediately. | **Pass** |
